# Product Profitability Analytics — Design Spec

**Date:** 2026-05-04
**Author:** Kasper Simonsen (with Claude)
**Status:** Approved — ready for implementation plan

---

## 1. Purpose

Give manufacturers a single place to answer two questions:

1. **Per job:** "How profitable was Order #1042, and where did the costs land?"
2. **Per product:** "Across all orders, what margin am I actually making on Steel Gate v2?"

Today the beta customer tracks nothing. Any number is better than zero, but the goal is accurate margin — which requires sell price to flow in from Shopify (currently broken) and actual labor costs to be included alongside planned material costs.

This is sub-system A of a broader financial module. Sub-systems B (capacity optimisation), C (shop floor dispatching), and D (customer order status) are explicitly out of scope here.

---

## 2. Context

- **Product:** Assemblio — Shopify-native MRP, AU/NZ market, pre-launch SaaS
- **Industry:** Non-specific manufacturing / assembly. No domain-specific terminology in the UI.
- **Beta customer state:** Tracks nothing today. Needs financial visibility before operational features.
- **Existing financial foundation:**
  - `job_cost_snapshot` — planned costs per order line (generated by `generate_job_financial_plan` RPC)
  - `job_cost_actual_rollup` — actual labor + overhead per order line (updated by `create_job_actual_time_entry` RPC)
  - `job_actual_time_entry` — individual time entries with `labor_cost_amount`
  - `department`, `cost_rate_schedule`, `staff_member` — rate infrastructure already built
- **Known blocker:** `order_line.unit_sell_price` and `line_sell_price` are always `0` because the Shopify sync GraphQL query never fetches price fields. The financial planning RPC correctly reads `line_sell_price` into `job_cost_snapshot.sell_price`, so fixing the upstream sync is sufficient.

---

## 3. MVP Scope

**In scope:**

- Fix Shopify sell price capture
- Per-job profitability view (planned vs actual, cost breakdown by category)
- Per-product rollup view (aggregate across all jobs for a variant)
- Re-sync prices for existing orders

**Explicitly post-MVP:**

- Actual material usage entry per job (`job_actual_material_entry` table)
- Capacity optimisation recommendations (sub-system B)
- Shop floor job dispatching and staff clock-on/off (sub-system C)
- Customer-facing order status updates (sub-system D)

## 4. Architecture

### 4.1 Shopify sell price fix

**File:** `src/lib/shopify/sync.ts`

Expand the GraphQL line items query to include:

```graphql
lineItems(first: 100) {
  nodes {
    quantity
    variant { id }
    discountedUnitPriceSet { shopMoney { amount } }
  }
}
```

Use `discountedUnitPriceSet` (what the customer actually paid after discounts). Map to:

- `unit_sell_price = discountedUnitPriceSet.shopMoney.amount` (as numeric)
- `line_sell_price = unit_sell_price × quantity`

Include both in the `order_line` upsert payload. The existing `generate_job_financial_plan` RPC already reads `order_line.line_sell_price` into `job_cost_snapshot.sell_price` — no RPC changes needed.

**Re-sync for existing orders:** Add a one-time server action `resyncOrderPrices()` that re-fetches all orders for the tenant from Shopify and patches `unit_sell_price` and `line_sell_price`. Exposed as a button in Settings (admin only) for beta. Not a background job — explicit trigger.

### 4.2 Cost breakdown — already in schema (no migration needed)

Both tables already have full cost breakdown columns:

- `job_cost_snapshot`: `planned_material_cost`, `planned_labor_cost`, `planned_admin_cost`, `planned_electricity_cost`, `planned_gas_cost`, `planned_overhead_cost` — all populated by the existing `generate_job_financial_plan` RPC.
- `job_cost_actual_rollup`: `actual_material_cost`, `actual_labor_cost`, `actual_admin_cost`, `actual_electricity_cost`, `actual_gas_cost`, `actual_overhead_cost`, `actual_margin`, `actual_margin_pct` — all populated by the existing `create_job_actual_time_entry` RPC.

The `create_job_actual_time_entry` RPC already seeds `actual_material_cost` from `job_cost_snapshot.planned_material_cost` (since actual material usage tracking is post-MVP). No schema or RPC changes are needed for the cost breakdown.

**For the UI cost breakdown display**, group the existing columns into three user-facing buckets:
- **Materials** → `planned_material_cost` / `actual_material_cost`
- **Labor** → `planned_labor_cost` / `actual_labor_cost`
- **Overhead** → sum of `planned_admin_cost + planned_electricity_cost + planned_gas_cost + planned_overhead_cost` / equivalent actuals

### 4.4 `product_profitability` database view

A Postgres view aggregated by variant, joined through `order_line`:

```sql
create or replace view public.product_profitability as
select
  sv.id                                          as variant_id,
  sv.title                                       as variant_title,
  sp.title                                       as product_title,
  count(jcs.id)                                  as job_count,
  sum(jcs.sell_price)                            as total_revenue,
  avg(jcs.planned_margin_pct)                    as avg_planned_margin_pct,
  avg(jcar.actual_margin_pct)                    as avg_actual_margin_pct,
  sum(jcar.actual_margin)                        as total_actual_margin
from public.order_line ol
join public.job_cost_snapshot jcs  on jcs.order_line_id = ol.id
join public.shopify_variant   sv   on sv.id = ol.variant_id
join public.shopify_product   sp   on sp.id = sv.product_id
left join public.job_cost_actual_rollup jcar on jcar.order_line_id = ol.id
group by sv.id, sv.title, sp.title;
```

The view is tenant-scoped via row-level security inherited from the underlying tables.

### 4.5 Margin status logic

Used in both views to label each row:

| Condition | Status label | UI treatment |
|---|---|---|
| `job_cost_actual_rollup` exists with `actual_total_cost > 0` | **Actual** | Green badge |
| `job_cost_snapshot` exists, no actuals | **Planned** | Grey badge |
| No snapshot | **Not planned** | Yellow warning badge |

## 5. UI Structure

### 5.1 Navigation

New sidebar item: **Profitability** — positioned after Costing. Route: `/app/profitability`.

### 5.2 By Job tab

Table columns:

| Column | Source |
|---|---|
| Order # | `orders.order_number` |
| Product | `shopify_product.title` |
| Variant | `shopify_variant.title` |
| Qty | `order_line.quantity` |
| Sell Price | `job_cost_snapshot.sell_price` |
| Cost | `actual_total_cost` if Actual, else `planned_total_cost` |
| Margin $ | Sell Price − Cost |
| Margin % | Margin $ ÷ Sell Price × 100 |
| Status | Actual / Planned / Not planned |

Note: `orders` does not currently store customer name. Customer is omitted from this view for MVP — the order number links through to the full order detail page where customer context lives.

Default sort: Margin % ascending (worst performers first).

Filters: date range (order created date), status (Actual / Planned / Not planned).

**Row expansion (inline):** Clicking a row expands to show cost breakdown:

```
                  Planned    Actual
Materials         $180       $180*
Labor              $95       $112
Overhead           $35        $38
─────────────────────────────────
Total cost        $310       $330
Sell price        $450       $450
Margin            $140       $120  (27%)
```

*Actual material = planned material for MVP (asterisked in UI with tooltip: "Actual material usage tracking coming soon").

If status is Planned (no actuals), the Actual column is omitted.

### 5.3 By Product tab

Table columns:

| Column | Source |
|---|---|
| Product | `product_profitability.product_title` |
| Variant | `product_profitability.variant_title` |
| Jobs | `product_profitability.job_count` |
| Total Revenue | `product_profitability.total_revenue` |
| Avg Margin % | `avg_actual_margin_pct` if available, else `avg_planned_margin_pct` |
| Total Margin $ | `product_profitability.total_actual_margin` |

Default sort: Avg Margin % ascending.

Clicking a row navigates to the By Job tab pre-filtered to that variant — no separate drilldown page needed.

## 6. Data flow summary

```
Shopify webhook
  → sync.ts (expanded query fetches discountedUnitPriceSet)
  → order_line.unit_sell_price / line_sell_price populated

generate_job_financial_plan RPC
  → reads order_line.line_sell_price
  → writes job_cost_snapshot (sell_price + planned breakdown columns)

create_job_actual_time_entry RPC
  → writes job_actual_time_entry
  → updates job_cost_actual_rollup (actual breakdown columns)

product_profitability VIEW
  → aggregates job_cost_snapshot + job_cost_actual_rollup by variant

/app/profitability page
  → By Job tab: joins order_line + job_cost_snapshot + job_cost_actual_rollup
  → By Product tab: selects from product_profitability view
```

---

## 7. Out of scope (for this spec)

- **Actual material usage entry** — deferred post-MVP. Column `actual_material_cost` is added to schema now but populated from planned until the entry UI is built.
- **Xero / accounting integration** — separate feature; flagged in gap analysis as AU market hook.
- **FIFO / weighted average cost layers** — flagged in gap analysis; architectural shift, separate spec.
- **Charts and dashboards** — tables are sufficient for beta. Visualisations can be layered on once the data is trusted.
- **Sub-systems B, C, D** — capacity optimisation, shop floor dispatching, customer status updates.
- **Multi-currency** — AUD only for v1.

---

## 8. Acceptance criteria

1. A Shopify order with a real price syncs correctly — `order_line.unit_sell_price` matches the Shopify line item price.
2. Running the financial plan after that sync produces a `job_cost_snapshot` with correct `sell_price` and non-zero `planned_material_cost`, `planned_labor_cost`, `planned_overhead_cost` (these columns already exist and are populated by the existing RPC).
3. `/app/profitability` is accessible from the sidebar.
4. By Job tab shows all order lines with correct margin calculations and status badges.
5. Row expansion shows the cost breakdown; Actual column appears only when actuals exist.
6. By Product tab aggregates correctly — a variant with 3 jobs shows job_count = 3 and correct summed/averaged figures.
7. Clicking a By Product row filters the By Job tab to that variant.
8. The `resyncOrderPrices` action updates existing orders' sell prices.
9. No sell price shows as negative or greater than 100% margin (data validation on sync).
